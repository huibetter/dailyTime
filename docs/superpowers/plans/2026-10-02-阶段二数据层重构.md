# DailyTime 整体优化阶段二：数据层与 Repository 重构计划

## 1. 阶段目标

在不改变当前项目、文档、标签、排期和设置用户体验的前提下，完成从“React 状态变化后全量同步”到“显式领域命令 + Repository 增量写入”的过渡。

本阶段完成后：

- React 页面不再直接决定 SQLite 的保存时机和保存粒度。
- 项目、文档、标签和设置拥有稳定的 Repository 接口。
- 桌面 SQLite 和浏览器 `localStorage` 实现同一组最小存储能力。
- 单个创建、更新、删除操作可以独立失败、重试和测试。
- 组合操作在桌面端具备明确事务边界，避免半条数据写入。
- 现有撤回能力有明确的领域快照或命令记录边界。

## 2. 当前问题与约束

### 当前问题

1. `src/main.jsx` 通过 `useEffect` 监听 `projects` 和 `docs`，变更后分别触发全量 SQLite 同步。
2. `saveDesktopProjects` 和 `saveDesktopDocuments` 同时承担映射、差异计算、SQL 执行和写入排队。
3. `RuntimeProject`、`RuntimeDocument` 与 `src/data/model.ts` 的领域模型重复，字段名称也不完全一致。
4. 数据库写入失败只能在应用层统一展示，无法指出具体命令或实体。
5. 浏览器适配器散落在页面状态 effect 中，桌面和浏览器行为容易逐渐分叉。

### 约束

- 本阶段不修改现有数据库表结构，不引入云同步或账号系统。
- 保留现有 `src/main.jsx` 页面交互，先换数据调用边界，再拆分页面组件。
- 保留旧数据读取兼容，升级期间不能因字段缺失导致空白页面。
- 暂不实现附件实体化存储；附件 Repository 留出接口即可。
- 每完成一个可验收子步骤，先通过测试再进行下一步改动。

## 3. 目标边界

```text
React 页面
  -> workspace commands / queries
    -> repository interfaces
      -> browser storage adapter
      -> desktop SQLite adapter
```

### 允许的依赖方向

- 页面可以依赖 domain 命令和查询。
- domain 可以依赖模型和 Repository 接口，不依赖 Tauri 或 `localStorage`。
- data/repositories 实现 Repository 接口，可以依赖数据库连接和 SQL。
- desktop 适配器可以依赖 Tauri，但页面不得直接依赖 Tauri SQL API。

### 禁止的依赖方向

- 页面组件直接调用 `openDatabase`。
- 页面组件直接写 `localStorage` 业务数据。
- Repository 读取 React state 或操作 DOM。
- 数据层为了兼容页面而暴露 SQL 行结构。

## 5. 实施步骤

### 步骤一：统一领域模型

- 以 `src/data/model.ts` 为基础，统一 `Workspace`、`Project`、`ProjectDocument`、`Tag`、`AppSettings` 类型。
- 明确运行时显示字段与持久化字段的转换，不再使用 `project`/`projectId`、`planned`/`plannedDate` 的混合命名作为 Repository 公共接口。
- 将状态、日期、时间、更新时间和标签定义为可校验的输入类型。
- 为创建和更新分别定义项目、文档和设置输入类型。

验收：`src/main.jsx` 可以通过 mapper 得到当前 UI 所需结构，领域类型不依赖 Tauri 类型。

### 步骤二：定义 Repository 合约

- 定义项目列表、创建、更新、删除。
- 定义文档按项目列表、查询、创建、更新、删除。
- 定义标签关联更新，避免页面自己拼接标签 SQL。
- 定义设置读取与保存。
- 所有方法返回领域模型或 `void`，错误统一为可识别的 `StorageError`。

建议合约：

```ts
interface WorkspaceRepository {
  load(): Promise<WorkspaceSnapshot>;
  createProject(input: CreateProjectInput): Promise<Project>;
  updateProject(id: string, input: UpdateProjectInput): Promise<Project>;
  deleteProject(id: string): Promise<void>;
  createDocument(input: CreateDocumentInput): Promise<ProjectDocument>;
  updateDocument(id: string, input: UpdateDocumentInput): Promise<ProjectDocument>;
  deleteDocument(id: string): Promise<void>;
  saveSettings(input: AppSettingsPatch): Promise<AppSettings>;
}
```

验收：Repository 接口可以在不引入 SQLite 的情况下被内存测试替身实现。

### 步骤三：建立 mapper 和浏览器适配器

- 将数据库行、旧版运行时对象和领域模型之间的转换集中到 mapper。
- 浏览器端只通过 `BrowserWorkspaceRepository` 读写 `localStorage`。
- 保留当前 `dt-projects`、`dt-docs` 和设置键，避免破坏已有浏览器预览数据。
- 读入异常数据时使用统一默认值并记录可展示的恢复提示。
- 为保存操作增加版本字段或命名空间，避免未来与旧快照格式冲突。

验收：浏览器模式的创建、编辑、删除、刷新恢复与当前行为一致；旧数据可读取。

### 步骤四：改造桌面 SQLite 适配器

- 将现有 `loadDesktopState` 的查询与 mapper 分离。
- 将项目、文档、标签写入改成显式方法，不再按数组计算删除差异。
- 文档更新在一个事务中完成文档字段与标签关联更新。
- 项目删除在一个事务中完成相关文档和关联数据清理，依赖数据库级联约束。
- 保留写入队列，但队列只负责串行化命令，不负责推断业务差异。
- 统一 SQL 错误包装，带上操作名和实体 ID，但不向用户暴露 SQL 细节。

验收：单个操作失败时不会覆盖其他实体；重启后数据一致；标签关联不会残留。

### 步骤五：引入 Workspace commands

- 在 App 层创建 `loadWorkspace`、`createDocument`、`updateDocument`、`deleteDocument` 等命令。
- 命令负责生成 ID、更新时间、标题规范化、输入校验和调用 Repository。
- 页面只更新临时 UI 状态并调用命令，不再通过 `setDocs` 触发持久化副作用。
- 保存状态由命令返回值驱动，保留当前顶栏保存状态展示。
- 撤回先继续使用有限快照，待增量写入稳定后再评估命令日志。

验收：新增/编辑/删除文档不再触发全量文档同步；保存失败能定位到具体操作并可重试。

### 步骤六：逐步删除旧入口

- 为旧的 `loadDesktopState`、`saveDesktopProjects`、`saveDesktopDocuments` 增加迁移注释。
- 所有页面调用切换到 Repository/commands 后，再删除旧的全量保存方法。
- 更新桌面开发文档，明确数据访问边界和浏览器/桌面差异。
- 增加回归测试，确认升级前数据和新数据格式均可读取。

验收：代码搜索不再发现页面直接调用旧保存入口；质量检查和构建完整通过。

## 6. 测试计划

### 单元测试

- 领域模型默认值和输入校验。
- 数据库行、旧运行时对象与领域模型的双向 mapper。
- 浏览器 Repository 的创建、更新、删除和损坏数据恢复。
- Repository 错误包装和 ID/更新时间生成。

### 集成测试

- 项目创建后创建文档，重启后仍可查询。
- 更新文档正文和标签时，标签关联保持一致。
- 删除项目后文档、标签关联和排期查询结果正确。
- 模拟单次 SQL 失败，验证状态不被错误覆盖。

### 回归测试

- 当前项目切换、总排期、项目排期和搜索。
- Markdown 标题同步、导出、撤回、粘贴图片。
- 浏览器预览与 Tauri 桌面两种存储模式。

## 7. 提交拆分建议

阶段二建议拆成以下本地提交，任何一个提交都应可运行：

1. `refactor: 统一领域模型和存储输入类型`
2. `refactor: 增加 workspace repository 合约与 mapper`
3. `refactor: 接入浏览器 workspace repository`
4. `refactor: 接入桌面 sqlite workspace repository`
5. `refactor: 用 workspace commands 替换全量保存 effect`
6. `test: 补齐 repository 和保存失败回归用例`

最终阶段二完成后再创建汇总提交，提交前必须通过类型检查、单元测试、隔离构建和格式检查。

## 8. 阶段二完成定义

- 页面不直接访问 `localStorage` 业务键或 SQLite。
- 全量 `saveDesktopProjects`/`saveDesktopDocuments` 不再作为正常写入路径。
- Repository 合约和两种适配器均有自动化测试。
- 事务性写入和错误状态可验证。
- 现有功能和数据兼容回归通过。
- 阶段完成历史已更新，并已创建本地 Git 提交。
