# DailyTime 整体优化方案

## 1. 方案目标

本方案面向 DailyTime 当前的桌面版基线，目标不是一次性重写，而是在保持现有项目、文档、排期和标签功能可用的前提下，逐步建立可维护、可测试、可发布的数据型桌面应用架构。

核心目标：

1. 将页面展示、业务状态、数据访问和 Tauri 能力解耦。
2. 将“全量状态快照写回数据库”改为可追踪、可回滚、事务化的领域操作。
3. 建立 TypeScript 类型、数据库迁移、错误处理、测试和 CI 质量门禁。
4. 优先保证离线可用、数据安全和升级兼容，再考虑同步、账号和多人协作。
5. 控制单次迭代风险，每个阶段都能独立验收和回退。

本方案参考以下 GitHub 开源项目的公开工程实践：

- [Tauri](https://github.com/tauri-apps/tauri)：桌面能力边界、Capability 权限模型和插件化集成。
- [Tauri plugins-workspace](https://github.com/tauri-apps/plugins-workspace)：官方插件组织方式及 SQL 插件的迁移/权限思路。
- [Joplin](https://github.com/laurent22/joplin)：离线优先的数据模型、同步边界、导入导出和回归测试思路。
- [AppFlowy](https://github.com/AppFlowy-IO/AppFlowy)：本地优先产品、前后端分层和可演进的领域模型。

## 2. 当前基线诊断

### 2.1 已有基础

- 已采用 React、Vite、TypeScript、Tauri 2 和 SQLite。
- 已有项目、文档、标签、附件预留表和应用设置表。
- 已有 SQLite 初始迁移、桌面端写入串行化和 Linux 构建流水线。
- 已有格式化、TypeScript 检查、前端构建和 Rust 检查命令。
- 当前核心功能包括文档编辑、项目排期、标签管理、Markdown 导出和撤回。

### 2.2 主要问题

| 优先级 | 问题 | 当前表现 | 风险 |
| --- | --- | --- | --- |
| P0 | 页面职责过重 | `src/main.jsx` 约 1,500 行，包含路由、状态、数据操作、编辑器和页面组件 | 修改互相影响，难以测试和定位回归 |
| P0 | 数据写入粒度过大 | 项目或文档状态变化后，按数组全量同步 SQLite | 数据量增长后写放大，删除和并发失败难处理 |
| P0 | 错误状态不完整 | 数据库初始化和保存失败主要写入控制台 | 用户无法判断是否保存成功，存在误操作风险 |
| P1 | 类型边界不统一 | 核心页面仍为 JSX，运行时模型与数据库模型存在字段转换 | 重命名字段或新增字段容易出现静默数据丢失 |
| P1 | Markdown 编辑器自研解析 | 手写 HTML/Markdown 转换并使用 `dangerouslySetInnerHTML` | XSS、格式丢失、粘贴和复杂 Markdown 兼容性风险 |
| P1 | 测试体系缺失 | 未发现前端单元测试、组件测试、E2E 或 Rust 集成测试配置 | 迭代只能依赖人工回归 |
| P1 | 权限范围偏宽 | Capability 使用 `fs:default`、`sql:default` 和 `sql:allow-execute` | 桌面攻击面和审计成本增加 |
| P2 | 发布链路不完整 | 当前主要验证 Linux 构建，缺少跨平台矩阵和安装升级验收 | 发布后才暴露平台或迁移问题 |
| P2 | 备份/恢复未闭环 | 附件、`.dailytime` 备份和恢复尚未实现 | 数据迁移和故障恢复能力不足 |

### 2.3 优化原则

- **先稳定数据，再重构界面**：数据库、写入事务和恢复能力优先于视觉重做。
- **保留可运行路径**：每次重构都保留浏览器预览和 Tauri 桌面两条运行路径。
- **单一事实来源**：业务数据以 SQLite 为事实来源，UI 只保存临时编辑状态。
- **显式失败**：保存失败、迁移失败、导入失败必须进入可见错误状态，不能只记录日志。
- **窄权限默认**：只授予当前功能所需的 Tauri capability，新增能力必须有说明。
- **可测量交付**：每阶段必须有命令、数据和用户场景三类验收条件。

## 3. 目标架构

### 3.1 前端分层

建议逐步从当前单文件结构演进为：

```text
src/
  app/
    App.tsx                 # 应用启动、路由和全局错误边界
    providers/              # 存储、主题、通知、快捷键
  features/
    projects/               # 项目列表、项目编辑、项目用例
    documents/              # 文档列表、编辑器、标签
    schedule/               # 日历、排期筛选和跳转
    settings/               # 设置和版本检查
  components/
    ui/                     # Button、Dialog、Toast、EmptyState 等
    layout/                 # 顶栏、侧栏、页面布局
  domain/
    models.ts               # 业务实体和值对象
    commands.ts             # 创建、更新、删除等命令
    errors.ts               # 可展示的领域错误
  data/
    repositories/           # Project、Document、Tag、Settings repository
    mappers/                # DB 行与领域模型转换
    storage.ts              # 浏览器/桌面存储适配器
  desktop/
    bridge.ts               # Tauri API 的唯一入口
    files.ts                # 附件、导入、导出
  lib/
    dates.ts
    markdown.ts
    validation.ts
```

迁移期间允许保留 `main.jsx`，但新增功能不得继续堆叠到该文件；每完成一个功能域，就把对应状态、组件和测试迁出。

### 3.2 数据访问边界

```text
React feature
  -> domain command/use case
    -> repository interface
      -> desktop adapter / browser adapter
        -> SQLite / localStorage
```

页面不得直接执行 SQL、读取文件路径或调用 Tauri API。浏览器预览继续支持轻量适配器，但两种存储适配器必须实现相同的领域接口，避免桌面和浏览器行为逐渐分叉。

### 3.3 数据库策略

1. 保留 SQLite 作为桌面端事实来源，所有结构变化新增迁移文件，例如 `002_attachments.sql`。
2. 每个用户操作对应一个 repository 方法或领域命令，不再由 React effect 对数组做全量同步。
3. 组合操作使用事务，例如删除项目、级联删除文档和清理附件记录必须原子完成。
4. 为 `documents.updated_at`、标签查询、排期查询和全文搜索预留索引方案。
5. 增加数据版本、备份格式版本和应用版本三个独立概念，禁止用应用版本替代数据库版本。
6. 对状态、日期、时间、标题和标签做统一校验，数据库约束作为最后一道防线。

建议的 repository API：

```ts
interface DocumentRepository {
  listByProject(projectId: string): Promise<ProjectDocument[]>;
  getById(id: string): Promise<ProjectDocument | null>;
  create(input: CreateDocumentInput): Promise<ProjectDocument>;
  update(id: string, patch: UpdateDocumentInput): Promise<ProjectDocument>;
  remove(id: string): Promise<void>;
}
```

### 3.4 桌面能力与安全

- Rust/Tauri 只提供文件、备份、系统路径、窗口和必要的数据库能力，不承载 React 页面规则。
- `capabilities/default.json` 按功能拆分权限，优先移除不必要的 `fs:default` 和宽泛 SQL 权限。
- 附件只允许写入应用数据目录，数据库保存相对路径和元数据，不把任意本机绝对路径注入页面。
- Markdown 预览使用成熟解析器，并对 HTML、链接协议、本地图片和外部资源做白名单处理。
- 生产环境启用明确 CSP；外部更新检查、导出和导入都要有超时、大小限制和错误提示。

## 4. 分阶段实施路线

### 阶段一：质量基线与可观测性（P0）

**目标**：在不改变主要功能的情况下建立可回归的工程底座。

- 将 `main.jsx` 中日期、Markdown、标题、文件名等纯函数迁入 `src/lib/`。
- 把核心模型迁移为 `.ts/.tsx`，开启更严格的 TypeScript 检查。
- 引入 ESLint、Vitest 和 React Testing Library；先覆盖纯函数、数据映射、状态转换。
- 增加统一的 `AppError`、Toast/错误面板和保存状态：保存中、已保存、失败、重试。
- 在 CI 中加入格式检查、类型检查、单元测试、前端构建和 `cargo clippy -- -D warnings`。

**验收**：核心纯函数有自动测试；保存失败可在界面看到；CI 能阻止格式、类型或测试失败的合并。

### 阶段二：状态与数据层重构（P0）

**目标**：消除组件对数据库和全量快照保存的直接依赖。

- 建立 `ProjectRepository`、`DocumentRepository`、`TagRepository` 和 `SettingsRepository`。
- 引入 `useWorkspace` 或等价的应用状态层，页面只派发命令并消费查询结果。
- 将项目、文档和设置保存从 `useEffect` 全量同步改为显式增删改操作。
- 为每个写操作建立事务边界和错误回滚；保留撤回所需的领域快照或操作记录。
- 为浏览器端实现同构适配器，明确哪些能力仅桌面端可用。

**验收**：创建、编辑、删除、重启恢复和撤回均通过 repository；任一保存失败不会把错误状态覆盖成“成功”。

### 阶段三：编辑器与交互可靠性（P1）

**目标**：提升 Markdown 内容安全、输入稳定性和可访问性。

- 用成熟 Markdown AST/解析库替换当前手写 `md` 与 `htmlToMarkdown` 双向转换。
- 明确 Markdown 原文为主数据，编辑器状态与保存状态分离，避免每次渲染重置光标。
- 增加粘贴图片、链接、代码块、列表、标题和撤销/重做的回归用例。
- 为删除、导入、覆盖工作区和清空操作统一使用可访问的确认对话框。
- 补充键盘导航、焦点管理、空状态、加载状态和窄窗口布局测试。

**验收**：复杂 Markdown 往返编辑不丢失主要结构；非法 HTML/协议不会执行；键盘可完成核心工作流。

### 阶段四：备份、附件和恢复（P1）

**目标**：让本地数据具备可迁移、可恢复能力。

- 实现 `.dailytime` 容器格式：清单、数据库快照、附件目录和格式版本。
- 导出前执行一致性检查；导入先写入临时目录，校验通过后再原子替换或新建工作区。
- 增加同名附件、超大附件、损坏备份、错误密码、磁盘空间不足和中断恢复测试。
- 先实现无密码备份，再增加可选的认证加密；密码错误不得修改当前数据。
- 在设置页展示最近备份时间、数据库版本和恢复入口。

**验收**：另一台设备可恢复完整项目、文档、标签和附件；任何导入失败都保持当前工作区不变。

### 阶段五：发布工程与跨平台验证（P1/P2）

**目标**：建立可重复发布、可回滚和可追踪的交付流程。

- CI 分为 `quality`、`build`、`bundle` 三层，质量门禁失败时不生成发布包。
- 增加 Windows 10/11 x64、Debian 13 amd64 和 macOS 的构建/验证矩阵；平台不可用时保留明确阻塞记录。
- 为 tag 发布生成校验和、版本说明和构建产物；不在构建脚本中混入环境相关路径。
- 验证全新安装、覆盖升级、数据库迁移、卸载后的数据保留策略和无网络启动。
- 自动更新暂不作为当前阶段阻塞项，先完善版本检查和手动升级说明。

**验收**：同一 tag 能生成可追踪产物；升级后数据库和附件可读；发布检查表全部通过。

## 5. 测试金字塔

### 单元测试

- 日期格式化、月份切换、排序和时区边界。
- 文档标题提取、Markdown 导出、文件名清理和输入校验。
- DB 行与领域模型转换、旧字段兼容和默认值。

### 集成测试

- 项目创建到文档创建、排期查询和项目删除的完整链路。
- 标签新增、重命名、删除及文档关联。
- SQLite 迁移、事务回滚、保存失败后的重试。
- 附件写入、数据库记录、删除清理和备份恢复。

### 端到端测试

- 首次启动空工作区。
- 创建项目和文档，关闭后重新打开并验证数据。
- 编辑 Markdown、设置排期、从日历跳转到文档。
- 导出、导入、错误导入不污染当前工作区。

### 发布测试

- Windows 安装包、Linux `.deb`/AppImage 和 macOS 包的启动检查。
- 低权限目录、无网络、只读文件、磁盘空间不足和异常退出。
- 数据库迁移从每个历史版本升级到当前版本。

## 6. 建议指标与完成定义

| 领域 | 第一阶段目标 | 稳定版本目标 |
| --- | --- | --- |
| 构建 | 格式、类型、单测、前端构建全部进入 CI | 发布包只从质量门禁通过的提交生成 |
| 前端复杂度 | `main.jsx` 降至 600 行以内 | 页面按 feature 拆分，单组件原则上不超过 300 行 |
| 数据保存 | 所有写入有明确成功/失败状态 | 无全量快照写回，组合写入均有事务 |
| 测试 | 覆盖核心纯函数和 repository | 核心工作流有集成/E2E 回归 |
| 数据安全 | 迁移可重复执行且失败可诊断 | 备份导入失败不改变当前数据 |
| 性能 | 100 条文档下编辑无明显卡顿 | 1,000 条文档下列表、搜索和排期仍可用 |
| 安全 | 收窄 capability，限制本地资源加载 | 生产 CSP、输入校验和外部资源策略完整 |

## 7. 暂不实施的事项

以下能力暂不纳入本轮优化主线，避免过早引入复杂度：

- 真实账号、云同步、多人协作和服务端权限。
- 复杂的记录级冲突合并和离线多端同步协议。
- 移动端、系统托盘、后台常驻和自动更新。
- 在没有性能证据前引入重量级全局状态框架或微前端。
- 在备份、迁移和错误恢复稳定前进行大规模视觉重做。

## 8. 首个迭代建议

建议下一轮只实施阶段一的最小闭环：

1. 增加 Vitest、React Testing Library 和 ESLint 基线。
2. 把纯函数、模型和存储映射迁出 `main.jsx`。
3. 增加统一错误状态与保存状态。
4. 将质量检查接入现有 Linux workflow。
5. 完成后再开始 repository 重构，不同时改数据库结构和编辑器。

这样可以先获得可回归能力，再逐步替换数据访问方式，降低一次性重构造成数据回归的风险。
